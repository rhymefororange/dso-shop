# Архітектура DSO-Shop

Документ описує компоненти навчального застосунку DSO-Shop, способи його розгортання і потоки даних між компонентами. Він є вихідним матеріалом для побудови діаграми потоків даних (DFD) і моделі загроз у ЛР1. Межі довіри, активи та загрози в документі навмисно не визначено — це завдання лабораторної роботи.

## 1. Призначення

DSO-Shop — інтернет-магазин тематичних товарів: каталог із пошуком, реєстрація і вхід покупців, кошик, оформлення замовлення з оплатою через зовнішній платіжний шлюз, адміністрування каталогу.

## 2. Компоненти

| Компонент | Технологія | Розташування в репозиторії | Призначення |
|---|---|---|---|
| Вебфронтенд | Статичні HTML/CSS/JS | `app/static/` | Сторінка каталогу, пошук, вхід, кошик; звертається до REST API з браузера |
| API-застосунок | Python 3.12, Flask 3, gunicorn | `app/` | REST API (`/api/...`), бізнес-логіка, видача токенів доступу |
| — маршрути | Flask blueprints | `app/routes/` | HTTP-обробники: health, products, auth, cart, orders, payments, admin |
| — доступ до даних | DB-API (psycopg 3 / sqlite3) | `app/models/`, `app/db.py` | SQL-запити до бази даних, початкові дані |
| — сервіси | Python | `app/services/` | Токени JWT, інтеграція з платіжним шлюзом, надсилання пошти |
| База даних | PostgreSQL 17 (локально — SQLite) | `docker-compose.yml`, `infra/terraform/postgres.tf` | Користувачі, товари, кошики, замовлення |
| Платіжний шлюз DSOPay | Зовнішній HTTPS API (вигаданий) | `app/services/payments.py` | Створення платежів; сповіщення про результат оплати (webhook) |
| Поштовий сервіс | SMTP | `app/services/mailer.py` | Листи покупцям (відновлення пароля) |
| Сховище секретів | HashiCorp Vault (цільова схема для Kubernetes) | — | Джерело секретів, що передаються застосунку як змінні середовища |
| Специфікація API | OpenAPI 3.0 | `api/openapi.yaml` | Опис усіх ендпоінтів, схем і схеми автентифікації |
| CI/CD | GitHub Actions | `.github/workflows/` | Збирання, тести; конвеєри безпеки додаються в ЛР2–ЛР5 |
| Реєстр образів | GitHub Container Registry (ghcr.io) | — | Зберігання образів застосунку (ЛР5) |
| Платформа виконання | Docker Compose; Kubernetes (kind) | `Dockerfile`, `deploy/`, `infra/terraform/` | Локальний запуск і розгортання |

### 2.1. Ролі користувачів

- **Анонімний відвідувач** — переглядає каталог і шукає товари, реєструється, входить.
- **Покупець** (`customer`) — керує кошиком, оформлює замовлення, переглядає власні замовлення.
- **Адміністратор** (`admin`) — керує каталогом, переглядає всі замовлення.

Автентифікація — токен доступу JWT (HS256), який видає `POST /api/auth/login` і який передається в заголовку `Authorization: Bearer <token>`. Роль користувача зберігається в базі даних і перевіряється на кожному запиті до захищених ендпоінтів.

### 2.2. Дані

| Таблиця | Вміст |
|---|---|
| `users` | Логін, e-mail, хеш пароля (scrypt, Werkzeug), роль |
| `products` | Назва, опис, ціна, залишок на складі |
| `cart_items` | Вміст кошиків покупців |
| `orders`, `order_items` | Замовлення, позиції, сума, статус оплати, ідентифікатор платежу |

Журнали застосунку виводяться в stdout контейнера (gunicorn + модуль `logging`).

### 2.3. Конфігурація і секрети

Застосунок читає конфігурацію зі змінних середовища (`app/config.py`): `DATABASE_URL`, `SECRET_KEY`, `DSO_ADMIN_PASSWORD`, `PAYMENT_GATEWAY_URL`, `PAYMENT_API_KEY`, `PAYMENT_WEBHOOK_SECRET`, `SMTP_HOST`, `SMTP_PORT`. Локально значення задаються у файлі `.env` (шаблон — `.env.example`), у Kubernetes — через Secret, який у цільовій схемі заповнюється з Vault.

## 3. Розгортання

### 3.1. Локально (Docker Compose)

```
Браузер / curl ──HTTP :8080──▶ app (gunicorn + Flask) ──TCP :5432──▶ db (PostgreSQL)
```

### 3.2. Kubernetes (kind)

- `infra/terraform/` створює кластер kind, простір імен `dso-shop`, Secret `dso-shop-db` і PostgreSQL (Deployment + Service `postgres`).
- Застосунок розгортається маніфестами `deploy/k8s/` (Deployment `dso-shop`, контейнер `api`, Service `dso-shop`) або Helm-чартом `deploy/helm/dso-shop`.
- Якщо Secret `dso-shop-db` відсутній, застосунок використовує вбудовану SQLite-базу в `/tmp` (демонстраційний режим).

### 3.3. Конвеєр постачання

```
Розробник ──git push / PR──▶ GitHub ──▶ GitHub Actions (тести, збирання образу)
                                              │
                                              └──push──▶ ghcr.io ──pull──▶ Kubernetes
```

## 4. Потоки даних

| № | Джерело → Приймач | Протокол | Дані |
|---|---|---|---|
| F1 | Браузер → API | HTTP(S) | Запити каталогу і пошуку (`GET /api/products`, `/api/products/search?q=`) |
| F2 | Браузер → API | HTTP(S) | Облікові дані під час входу і реєстрації; у відповідь — токен доступу |
| F3 | Браузер → API | HTTP(S) + Bearer | Операції з кошиком і замовленнями (`/api/cart`, `/api/orders`) |
| F4 | Браузер адміністратора → API | HTTP(S) + Bearer | Керування каталогом (`/api/admin/...`) |
| F5 | API → PostgreSQL | PostgreSQL wire protocol, :5432 | SQL-запити: користувачі, товари, кошики, замовлення |
| F6 | API → DSOPay | HTTPS | Створення платежу (`POST /v1/payments`) з API-ключем у заголовку `Authorization` |
| F7 | DSOPay → API | HTTPS | Webhook про результат оплати (`POST /api/payments/webhook`, підпис HMAC-SHA256 у `X-DSOPay-Signature`) |
| F8 | API → SMTP-сервер | SMTP + STARTTLS | Листи покупцям |
| F9 | Vault → Kubernetes Secret → под API | HTTPS / змінні середовища | Секрети застосунку |
| F10 | GitHub Actions → ghcr.io → Kubernetes | HTTPS (OCI) | Образ контейнера застосунку |

## 5. Сценарії обробки ключових операцій

**Пошук товарів.** Браузер надсилає рядок пошуку в параметрі `q`; API формує SQL-запит до таблиці `products` і повертає список товарів у JSON.

**Оформлення замовлення.** Покупець додає товари до кошика (`POST /api/cart/items`) і викликає `POST /api/orders`. API обчислює суму за цінами з каталогу, створює замовлення зі статусом `pending`, звертається до DSOPay (F6) і зберігає ідентифікатор платежу. Без `PAYMENT_GATEWAY_URL` використовується режим пісочниці (без мережевих запитів).

**Підтвердження оплати.** DSOPay надсилає webhook (F7). API перевіряє HMAC-підпис спільним секретом `PAYMENT_WEBHOOK_SECRET`, відповідність ідентифікатора платежу і поточний статус замовлення, після чого змінює статус на `paid` або `failed`.
